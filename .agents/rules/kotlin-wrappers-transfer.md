# Publishing Generated Declarations to `kotlin-wrappers`

The generated tree is published by copying it into a fork of
[`JetBrains/kotlin-wrappers`](https://github.com/JetBrains/kotlin-wrappers) and opening PRs upstream. A local clone of
the fork is referred to as `FORK` below; its `master` tracks upstream `master` and must stay untouched — all work
happens on topic branches.

## Package → module map

Every `mui-kotlin/src/jsMain/kotlin/<pkg>` maps 1:1 onto `FORK/<module>/src/jsMain/generated/<pkg>` (same file set):

| Generated package             | Fork module                                                     |
|-------------------------------|-----------------------------------------------------------------|
| `mui/base`                    | `kotlin-mui-base`                                               |
| `mui/material`                | `kotlin-mui-material`                                           |
| `mui/system`, `mui/types`     | `kotlin-mui-system`                                             |
| `mui/icons/material`          | `kotlin-mui-icons-material`                                     |
| `mui/lab`                     | `kotlin-mui-lab`                                                |
| `muix/pickers`, `dateio/core` | `kotlin-muix-date-pickers`                                      |
| `muix/tree/view`              | `kotlin-muix-tree-view`                                         |
| `baseui`                      | — no module yet; **never transfer** (WIP Base UI migration)     |

Hand-written fork sources are out of scope and must not be touched:
`kotlin-mui-material/src/jsMain/kotlin/**`, `kotlin-muix-date-pickers/src/jsMain/kotlin/**`.

## Rules

*   **Rule #5: The generator is the single source of truth.** Never invent or fix declarations in the fork. If the
    fork's version of a file is "more right" (e.g. `js.date.Date` instead of `kotlin.js.Date`, a short name plus
    `import` instead of an inline FQN), fix the generator here first (`KotlinType.kt`, `DateIO.kt`, `IMPORTED_FQNS`
    in `Generator.kt`), rebuild, and only then transfer its output.
*   **One PR = one topic = one branch.** Version bumps, API fixes and formatting/import-only changes go into
    separate branches (past examples: ``MUI X `9.17.0` ``, ``MUI. Fix `SpeedDial.ariaLabel` and
    `useSlider.shiftStep` ``, ``MUI. Explicit imports instead of `react.*` ``). Apply only the generated hunks
    belonging to the requested topic; preserve unrelated differences, even within the same file.
*   **Diff-only handoff: never stage, commit, or push.** Leave the transferred changes as an unstaged working-tree
    diff on the target branch. Preserve existing user changes and the index. Do not use operations that create
    commits, including `git merge`, to prepare or verify the transfer. The human reviews, commits, pushes and opens
    the PR. [Rules #3–#4 in AGENTS.md](../../AGENTS.md) still apply to this repository itself.
*   **Always finish with a ready-to-use commit message.** The fork's message is a title only: no body,
    `Co-Authored-By` or any other attribution trailer. Use the topic's established title style from the examples above.
*   **Do not run compilation checks, builds or tests in the `kotlin-wrappers` fork.** This includes its examples and
    any temporary worktrees. Verify the transfer by inspecting the diff and Git state only. Required generation,
    compilation and tests in this generator repository remain part of source verification before transfer.
*   **Version bumps touch only `gradle/jspkg.versions.toml`.** `.kotlin-locks/**` is regenerated by the fork's
    "Package Lock" workflow after merge and must not be part of the transfer diff. Preserve any pre-existing user
    changes there; do not reset them.
*   The fork compiles with `allWarningsAsErrors = true` and MUI modules have only the `js` target (no `wasmJs`).
    `@file:Suppress(...)` blocks emitted by the generator are therefore required, not cosmetic.

## Workflow

1.  Rebuild here (`./gradlew :mui-kotlin:clean build`) and make sure `git diff -- mui-kotlin/src/jsMain/kotlin`
    contains exactly what you expect. This verification runs in the generator repository, not in the fork.
2.  Inspect the fork's branch, HEAD, working tree and index before changing anything. Use the target branch named
    by the user; otherwise create a topic branch from `master`. Keep `master` untouched and preserve existing changes.
    Establish the source commit range and exact topic being transferred.
3.  List the differences per mapped pair to identify candidate files:
    ```bash
    SRC=$PWD/mui-kotlin/src/jsMain/kotlin; FORK=/path/to/kotlin-wrappers
    for p in mui/base:kotlin-mui-base mui/material:kotlin-mui-material mui/system:kotlin-mui-system \
             mui/types:kotlin-mui-system mui/icons/material:kotlin-mui-icons-material mui/lab:kotlin-mui-lab \
             muix/pickers:kotlin-muix-date-pickers dateio/core:kotlin-muix-date-pickers muix/tree/view:kotlin-muix-tree-view; do
      diff -rq "$SRC/${p%%:*}" "$FORK/${p##*:}/src/jsMain/generated/${p%%:*}"
    done
    ```
    Differences from other topics or still-open PRs are not part of the transfer. For a scoped fix, use the
    generator delta for that fix rather than copying all differing files.
4.  Apply the selected generated delta to the target branch without staging or committing. Copy whole files only
    when their complete change belongs to the requested topic; otherwise apply the relevant hunks or use the
    three-way procedure below. For a version PR, apply only the requested toml bump as well.
5.  Inspect `git diff`, run `git diff --check`, and check `git status --short`. Confirm the transferred hunks match
    the intended generator delta, unrelated content is preserved, and HEAD and the index have not changed.
    Do not run compilation, builds or tests in the fork, its examples or worktrees.
6.  Report the target branch/worktree, changed files and diff summary. Explicitly state that the changes are
    uncommitted and unstaged, and provide the ready-to-use title-only commit message in the final response.

## When earlier transfer PRs are still open

`master` then lags the generator by those PRs, so copying whole files would drag their hunks into the new branches
(and the step-3 diff lists their files too). Before starting:

*   Check what upstream already took — no configured remote needed:
    `git fetch https://github.com/JetBrains/kotlin-wrappers.git master` (then `git log master..FETCH_HEAD`) and the
    public `https://api.github.com/repos/JetBrains/kotlin-wrappers/pulls?state=all` (`gh` may not be authenticated).
*   Confirm the baseline: the generator at the last transferred commit must equal `master` with the still-open (and
    merged-but-not-in-`master`) changes laid over it. Then the new topics are exactly the generator diff since that
    commit. When updating an existing PR branch, compare that branch with the generator immediately before the fix
    and preserve unrelated differences.
*   Use a separate `git worktree` when needed to protect the human's checkout. It is for preparing or inspecting
    diffs, not for compilation or tests. Keep each requested uncommitted topic diff available to the human and report
    its worktree path. Remove scratch worktrees at the end only after the requested diff is safely in its target
    checkout; never delete the only copy of the handoff diff.
*   Per file, three-way merge the generator delta onto the target branch's file instead of copying:
    `git merge-file <fork file> <generator@baseline> <generator@fix>` (added files: copy; deleted: `rm`, after
    checking the fork copy equals the old generator one). This merges file content without creating a Git commit.
    A conflict marks a file shared with an open PR — usually its import block. Resolve it consciously: an import
    the new code needs can go missing silently once both PRs land (`import react.*` in `master`, an explicit list
    without the new name in the open PR). Ask the human whether to put the import into the open PR, stack the branch
    on it, or take the generator's block and accept a conflict for whichever PR merges second.
*   If checking the union of several topics, reconstruct it in scratch files using patches or file-level merging,
    including the open PRs' changes. Compare against the corresponding generator snapshot; do not create merge
    commits or run fork builds/tests. A scoped transfer must match its intended delta, not the whole generator tree.
*   Scripts that split file lists should run under `bash`: the agent shell may be `zsh`, which does not word-split
    unquoted variables.
